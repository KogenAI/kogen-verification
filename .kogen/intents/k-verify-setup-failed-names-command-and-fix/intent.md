# Name the failing setup command and the fix

Slug: k-verify-setup-failed-names-command-and-fix
Model: not applicable — the change adds two fixed detail lines to one existing refusal; there is no state or interaction to model
Acceptance:
- .kogen/intents/k-verify-setup-failed-names-command-and-fix/acceptance.feature
- features/steps/k-verify-setup-failed-names-command-and-fix__steps.js

When a configured setup command fails, `Readiness.Setup` in `verify/readiness.go` refuses with `environment/setup_failed`. Today the refusal names only the internal step id (`setup-1`) and the exit status, followed by the command's output tail. The command text appears only in the earlier progress line on standard error, and the refusal does not say what to change. Shaping (`kogen intent shape`, through `Readiness.Setup` with reuse and through `Readiness.Check`), `kogen intent build` (through `Readiness.Setup` without reuse) and `kogen intent preflight` (through readiness, which runs the same `Setup`) all get this refusal from that one function, so the change is made there once.

After the change, a failing setup command at zero-based position `i` of `commands.setup` refuses with:
- The unchanged first line (the `*sys.Error` message): `environment/setup_failed: Setup setup-<i+1> failed (status=<n>).`, exit code 3.
- The unchanged detail lines from today: the output tail (`Tail(res.Output, 20)` without an Attempt, `Diagnostic(res.Output)` with one), in the same order.
- Then two added detail lines, in this order:
  1. `commands.setup[<i>]: <command>`, where `<command>` is the command exactly as written in `commands.setup`. It goes through the same redaction as the progress line (`r.Attempt.Redact`, which is nil-safe), so it is byte-identical to the configured command unless that command contains a secret pattern.
  2. For status 127: `next: the program was not found; fix commands.setup in .kogen/project.yaml (commit the change) or install what the command needs, then rerun the command that was refused`. For every other nonzero status: `next: fix commands.setup in .kogen/project.yaml (commit the change) or install what the command needs, then rerun the command that was refused`.

With a diagnostic Attempt, `Attempt.Refuse` keeps appending its step summary (`Steps that ran, with wall time …`, `Not run: …`, `Evidence: …`) after the refusal's lines, so the two added lines come after the output and before that summary. The printed form stays `sys.Error.Render`: the first line, then each detail line indented by two spaces. Because the output tail stays directly after the first line, a printed refusal still contains `environment/setup_failed: Setup setup-1 failed (status=4).\n  setup-broke\n` for that setup, as downstream tests in kogen-build expect.

Nothing else changes. The progress line `kogen: running setup-<i+1>: <command>` stays as it is. A passing setup prints none of the new lines. The setup stamp and reuse, the `setup-<n>` step names in logs, evidence, the attempt plan and the step summary, and the exit status 3 are all unchanged. No configuration, setting or new error class is added.

## Decisions
- Keep the first line byte-identical (`environment/setup_failed: Setup <id> failed (status=<n>).`), exit status 3 and the command's output tail. (source: request)
- Add exactly two detail lines: the failing command as written, labelled with its position `commands.setup[<i>]` (zero-based), and the next step `fix commands.setup in .kogen/project.yaml (commit the change) or install what the command needs, then rerun the command that was refused`. (source: request)
- For status 127 the next-step line also says that the program was not found. (source: request)
- Nothing is added to the successful path, and the progress line stays. (source: request)
- The added lines come after the existing output tail, and before a diagnostic Attempt's step summary. The command line comes first and the next-step line second. Their texts are `commands.setup[<i>]: <command>` and `next: …`, with `next: the program was not found; …` for status 127. This is a shaping decision on placement and exact wording. It keeps the output tail directly under the first line, where current callers and downstream tests read it. (source: request)
- Make the change once in verify.Readiness.Setup: after the existing output-tail lines, add `commands.setup[<i>]: <command>` (zero-based, redacted like the progress line) and then the next-step line. For status 127 that line is prefixed with `the program was not found; `. Readiness runs the declared Feasibility checks and the acceptance to establish them.) (source: request)

- Addressed: first line unchanged, exit 3, output tail kept. Every refusal scenario asserts the exact message, exit 3 and the first printed line. The exit-1 scenarios assert that the tail lines `first` and `setup-broke` precede the added lines. The 127 scenarios assert that detail line 1 is the shell's own `… definitely-not-a-program … not found` line.
- Addressed: the request's synthetic example. With `commands.setup` `['definitely-not-a-program --x']`, the refusal is `environment/setup_failed: Setup setup-1 failed (status=127).` with exit 3 and has the printed detail line `commands.setup[0]: definitely-not-a-program --x`. It also has a line naming `.kogen/project.yaml` that says the program was not found. This is asserted for shaping, a Build and a readiness check.
- Addressed: "With a setup command that exits 1 … the same two kinds; the output tail is still printed". - Addressed: "A passing setup command prints none of the new lines" and "the progress line stays". The progress lines are asserted exactly for each entry point. A passing `true` prints neither `commands.setup`, `.kogen/project.yaml` nor `next:`.
