# Confirm lost setup output does not reproduce

Slug: v-setup-failed-output-tail
Model: not applicable — no product behavior changes; this Intent only records executable evidence that the reported state does not occur
Acceptance:
- .kogen/intents/v-setup-failed-output-tail/acceptance.feature
- features/steps/v-setup-failed-output-tail__steps.js

Daily review 2026-11-05 h12 item 5 reported that a failed setup step can come back with no output at all. Build fix-k-verify-previously-red-first (MacBook, 5 Nov) printed `kogen: running setup-2: npm ci --prefix testdata/tools/quint`, then `environment/setup_failed: Setup setup-2 failed (status=134).`, then one empty indented line, then `shape did not produce an Intent`. Status 134 is an abort (SIGABRT). The suspected place is verify/readiness.go: the `res.Status != 0` branch after runStep for setup steps. Its `e.Lines` come from `Diagnostic(res.Output)` when an Attempt is set, and from `Tail(res.Output, 20)` otherwise. The request is to reproduce this first with a setup step that writes to stderr and then aborts (for example `sh -c 'echo boom >&2; kill -ABRT $$'`), and to show that the setup_failed outcome on current main has no line containing `boom`. If main already shows the output, the request is to stop and report that it does not reproduce, with no code change. Only if it reproduces should a failed setup step's outcome always carry the last lines (at most 20) of its combined stdout and stderr, also when the step was killed by a signal and when `Diagnostic` finds nothing to extract. The first line `environment/setup_failed: Setup setup-N failed (status=N).` stays unchanged. Every existing test stays green and nothing unrelated changes.

The scenario does not reproduce on main (5d5d2d3), so the outcome is the stop-and-report branch, with no product code change. The Build must not edit verify/readiness.go, verify/text.go, verify/env.go, verify/attempt.go or any other Go file, test or golden. The repository's existing behavior is the intended behavior and stays unchanged:
- runStep starts each setup command through kogen-loop's sys.Session, which writes the command's stdout and stderr to one capture buffer. The buffer keeps what the command wrote when the command is killed by a signal, and `res.Output` holds it. Kogen reports a shell killed by signal n as status 128+n (134 for SIGABRT).
- Without an Attempt, the setup_failed outcome's lines are `Tail(res.Output, 20)`: the last 20 lines of the combined output. With an Attempt, they start with `Diagnostic(res.Output)`: the whole output up to 60 lines, otherwise its first 30 and last 20 lines with a marker between, cut to 16 KiB. Readiness.Check then adds the attempt's step summary after those lines. Both paths keep the last lines of a non-empty output.
- The reported Build's empty line is consistent with an `npm ci` run that wrote nothing that the capture received before it aborted. Under this repository's code, empty captured output is the only way to get that line. Why that run wrote nothing is outside this repository's setup branch, and no change is specified for it.

The acceptance records this non-reproduction through the real Readiness.Check entry point on the request's example, with and without a diagnostic Attempt. It passes on the unchanged tree. It would fail if a signal-killed setup step lost its output, interleaved stdout and stderr out of order, changed the first line or exit code, or kept other than the last 20 lines on the Tail path.

## Decisions
- Attempt the reproduction first; because the scenario does not hold on main, stop and report non-reproduction with no code change. (source: request)
- Reproduce with a setup step that writes `boom` to stderr and then aborts: `sh -c 'echo boom >&2; kill -ABRT $$'`. (source: request)
- Keep every existing test green and make no unrelated changes; the Build changes no file outside this Intent's acceptance artifacts. (source: request)

## Source comparison
- Addressed: "add a test with a setup step that writes to stderr and then aborts … and show that the setup_failed outcome on current main has no line containing `boom`". Scenarios 1 and 2 run exactly `sh -c 'echo boom >&2; kill -ABRT $$'` as setup-2, after `true` as setup-1, through Readiness.Check without and with a diagnostic Attempt. The outcome is `environment/setup_failed: Setup setup-2 failed (status=134).` with exit 3, and a line contains `boom`. Without an Attempt the lines are exactly [`boom`]; with one they start with `boom`. It does not reproduce.
- Addressed: "This holds when the step was killed by a signal". Scenarios 3 and 4 abort the setup shell itself with `echo out; echo err >&2; kill -ABRT $$`, without and with an Attempt. Both keep `out` then `err` in order, which is combined stdout and stderr, under status 134.
- Addressed: "the last lines … (at most 20 lines)" on the Tail path. Scenario 5 writes `seq 1 30` to stderr and aborts; the lines are exactly `11` through `30`. The existing TestSetupFailureStopsAtTheFirstFailedCommandWithItsLastLines already covers the same bound for a normal exit.
- Addressed: "If main already shows the output, stop and report that it does not reproduce (no code change)": no product edit is specified.
- Addressed: the first line `environment/setup_failed: Setup setup-N failed (status=N).` is asserted exactly and stays unchanged.
- Superseded by non-reproduction: the conditional fix, which would make the outcome always carry at most 20 last lines, also with an Attempt and when `Diagnostic` finds nothing. With an Attempt, the existing `Diagnostic` path keeps the output whole up to 60 lines, or its first 30 and last 20 lines, so the last lines are always present. It is unchanged because the request makes the fix conditional on reproduction. `Diagnostic` returns empty text only for empty or whitespace-only output, and `Tail` does too.
- Noted, not reproduced here: the MacBook Build's empty line under `npm ci --prefix testdata/tools/quint` (status 134). This repository's setup branch carries any captured output. A local real `node -e 'process.stderr.write("boom\n"); process.abort()'` setup step kept its output, including Node's abort stack trace. Without an Attempt, the 20-line tail of that long stack trace no longer includes `boom`, which is the specified Tail bound, not lost output. No change is specified for it.
