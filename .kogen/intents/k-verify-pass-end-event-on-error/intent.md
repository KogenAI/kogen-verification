# Log pass_aborted when a verification pass errors

Slug: k-verify-pass-end-event-on-error
Model: not applicable — a pass ends in exactly one of two terminal log events chosen by whether Verify returns an error; there are no interacting states or transitions to model
Acceptance:
- .kogen/intents/k-verify-pass-end-event-on-error/acceptance.feature
- features/steps/k-verify-pass-end-event-on-error__steps.js

A verification pass (`Verify` in `verify/run.go`, which `Run` calls after the fixers and which readiness and Builds use) that completes keeps writing its `pass` event exactly as now. A pass that stops with an error instead now ends with exactly one `pass_aborted` event, so a reader of the run log can tell a dead pass from a running one, which item was running and how much of the pass finished.

1. A pass starts when `Verify` is entered (it prints `kogen: verifying (pass N)`). Every return of `Verify` with a non-nil error, from the first tree read to the final tree comparison, first logs to `in.Log` (a nil Logger records nothing, as now) exactly one event with exactly these keys:
   `{"event":"pass_aborted","pass":<in.N>,"cause":<cause>,"item":<item>,"completed":[<names>],"checks_wall_ms":<int>}`
   It is the last event the pass logs, after every `command`, `step_sweep` and `command_result` event of the pass. The existing deferred removal of the scratch directory stays, so the scratch directory never outlives `Verify`.
2. `cause` is one fixed word, decided in this order:
   - `cancelled`: `errors.Is(err, context.Canceled)`, or the error is the session's interrupt (`errors.As` a `*sys.Interrupted`).
   - `timeout`: `errors.Is(err, context.DeadlineExceeded)`, or the error is an approval step that exceeded its bound (`*stepTimeout`).
   - `baseline_changed`: the error is the refusal returned by the baseline guard `in.Intact` that runs after the pass's commands.
   - `tree_error`: the error came from reading, materializing or comparing the candidate tree: `repo.Tree` (before or after the checks), `repo.Materialize`, `repo.Changed` (the maintained-spec comparison or the after-checks comparison) or `mat.Mutations`.
   - `runner_error`: the error was returned while running an item: `runLogged` (setup commands, stage checks and project checks), `RunAcceptance`, `runFeature` (maintained features), `CheckModel` (the Intent's model and maintained models) or `runCohort` (concurrent Go checks).
   - `other`: any other error, for example creating the check-report folder or `.kogen/local`, a declared maintained specification or implementation path missing from the candidate (`checkDeclaredExist`), or listing the acceptance suite (`suiteFiles`).
3. `item` is the name of the item whose execution returned the error, whether it had started its command or failed before starting it (for example `second` when its runner could not start it). For an error from a concurrent cohort of Go checks it is the first item of that cohort. It is `""` when the error happened outside an item: before the first item (tree read, materialize, folders, declared paths, suite listing) or after the last one (scratch mutations, baseline guard, after-tree read and comparison).
4. `completed` lists, in the order the pass recorded their results, the names of the items that finished in this pass: every setup command, acceptance, model, maintained model, maintained feature and check whose result the pass recorded, red or green, including speculative cohort results. Items named in `not_run`, cancelled cohort results and the item named in `item` are not listed. It is `[]` (never `null`) when nothing finished.
5. `checks_wall_ms` is the integer number of milliseconds from the start of the pass's first item (the same start the `pass` event's `checks_wall_ms` uses) to the moment `Verify` handles the error; it is `0` when no item started.
6. Unchanged: the error returned to the caller is the same error value (not wrapped or replaced), the returned Pass value (`Pass{}` on error), exit codes, the progress text, every other event, and the `pass` event of a pass that returns without error, including its keys, values and `checks_wall_ms`. A pass that writes `pass` never writes `pass_aborted` and the other way round. The scratch directory and the other temporary folders of the pass are still removed.
7. Errors of `Fix` (the fixers and the baseline guard after each fixer, which `Run` executes before calling `Verify`) are not part of a pass and log no `pass_aborted`.

## Decisions
- The event is named `pass_aborted` and has exactly the keys `event`, `pass`, `cause`, `item`, `completed` and `checks_wall_ms`; `cause` is one of `runner_error`, `baseline_changed`, `cancelled`, `timeout`, `tree_error`, `other`. (source: request)
- `completed` lists every item that finished, so for the stub project the acceptance item, which runs before the checks, is listed together with the checks `first` and `second`. (source: request)

## Source comparison
- Addressed: Problem and Need, one `pass_aborted` as the last event of every pass that started and does not reach its `pass` event, with `pass`, `cause`, `item`, `completed` and `checks_wall_ms` measured to the abort: outcome items 1 to 5 and every aborted scenario, which compares the whole masked event log of the pass with the control log of the unchanged tree plus the one final `pass_aborted`.
- Addressed: the stub project with checks `sleep 1` and `true` (named `first` and `second`) on the verify tests' stub project, run through the real `Verify` by a Go driver compiled into the verify test binary. The request's "fake runner" is realized without a production seam (testing rule 4): the driver makes the real runner fail on the second check by pointing `TMPDIR` at a missing folder when the second check's `command` event is logged, so the runner cannot create the step's marker file and returns that error before starting the command; it cancels the context 300 ms after the first check's `command` event; it runs the timeout case under an approval Attempt whose step bound is 500 ms; it installs a baseline guard that refuses after the checks; and it starts the tree-error case from the missing commit `0000000000000000000000000000000000000000`.
- Addressed: synthetic acceptance 1, scenario "A runner failure on the second check ends the pass with one runner_error pass_aborted event": `cause: runner_error`, `item: second`, `completed: ["acceptance","first"]`, no `pass` event, `checks_wall_ms` in [1000, 3000).
- Addressed: synthetic acceptance 2, scenario "Cancelling the context during the first check ends the pass with a cancelled pass_aborted event": `cause: cancelled`, `item: first`, `checks_wall_ms` in [300, 3000).
- Addressed: synthetic acceptance 3, scenario "A baseline guard refusal after the checks ends the pass with a baseline_changed pass_aborted event": `completed` lists every item (`acceptance`, `first`, `second`), `item` is empty, and the returned error is the guard's own refusal value (`same_as_guard_refusal: true`).
- Addressed: synthetic acceptance 4, scenarios "A normal green pass writes only its unchanged pass event" and "A normal red pass writes only its unchanged pass event": the whole masked log and the returned Pass JSON and progress equal the control captured on the unchanged tree; the `pass` event keeps an integer `checks_wall_ms`.
- Addressed: synthetic acceptance 5, every aborted scenario asserts that no `kogen-*` entry is left in the temporary folder, that the scratch directory named by the command events no longer exists, and that the returned error (Go type and text), the Pass JSON (`Pass{}`) and the progress text equal the control of the unchanged tree.
- Addressed beyond the five examples, because the Need names these causes: scenario "A check that exceeds its step bound ends the pass with a timeout pass_aborted event" and scenario "A tree-read failure before any item ends the pass with a tree_error pass_aborted event" (`item` empty, `completed` empty, `checks_wall_ms` 0). `other` is covered by a Go test.
- Test-scope qualification: the log comparisons remove what differs between identical runs or hosts on the unchanged tree: every `*_ms` key (so `checks_wall_ms` is asserted by its own step), the `ms` of `step_sweep`, the content of `check_identity` and `identity_sha256`, the random suffix of Kogen's temporary names and the numbering of the test's temporary folders.
- No requested behavior is omitted or superseded; the required slug, step-file name and step-sentence prefix are kept exactly.

## Tests
- A runner error on an item logs one pass_aborted with cause runner_error, the item and the finished items, and no pass event, returning the same error: new Go test in `verify` using `memLog`, plus the acceptance scenario (integration)
- A cancelled context or session interrupt logs cause cancelled naming the running item: extend `TestInterruptStopsThePassAndRemovesTheScratchFolder` with a `memLog` asserting the pass_aborted, plus the acceptance scenario (integration)
- A context deadline or an exceeded approval step bound logs cause timeout naming the running item: extend `TestWallTimeDeadlineAndNeverStarted` to assert `cause: timeout`, `item: setup-1`, plus the acceptance scenario (integration)
- A baseline guard refusal after the pass logs cause baseline_changed with every finished item and empty item, and a guard refusal after a fixer logs no pass_aborted: extend `TestBaselineGuardRunsAfterEachFixerAndAfterThePass` with a `memLog`, plus the acceptance scenario (integration)
- A tree-read failure before any item logs cause tree_error with empty item, empty completed and checks_wall_ms 0: new Go test in `verify`, plus the acceptance scenario (integration)
- Any other error, such as a declared maintained specification path missing from the candidate, logs cause other with empty item: new Go test in `verify` (integration)
- Green and red passes log only the unchanged pass event and the scratch directory is removed on every abort: existing pass and leftover tests plus the acceptance control comparisons (existing)

## Feasibility
- A scratch driver compiled into the verify test binary with `go test -c -overlay` (no checkout change) ran all seven cases on the unchanged tree and produced the control logs, errors, Pass JSON and progress embedded in the feature: the runner fault returned `*fs.PathError` "open <tmp>/…/missing/kogen-acceptance-marker-…: no such file or directory" before the second check started; the cancel returned "context canceled" after `first`'s command_result; the 500 ms Attempt bound returned `*verify.stepTimeout` "step command timed out" with status 143; the guard returned its own refusal value; the missing start commit returned `*git.CommandError` from `git read-tree`; no case left a `kogen-*` entry or scratch directory. Repeated cancel and timeout runs gave the same events. On the unchanged tree every aborted case logs no closing event, so its event assertion fails, and the green and red cases pass.
