# Reap adopted children while the shell runs

Slug: k-verify-acceptance-reaper-continuous-reap
Model: not applicable — one per-run wait loop that keeps the shell's status, followed by the unchanged one-shot stop loop; nothing persists between runs and no rules interact over time
Acceptance:
- .kogen/intents/k-verify-acceptance-reaper-continuous-reap/acceptance.feature

K-VERIFY-ACCEPTANCE-REAPER-CONTINUOUS-REAP (kogen-verification), reliability. Package `verify`, file `verify/sweep_linux.go` (`runAcceptanceReaper`), Linux only.

Today (the code does this now): on Linux every check, acceptance run and probe runs as `exec '<self>' --kogen-verification-acceptance-reaper '<script>'` (`acceptanceReaped`). The helper sets `prctl(PR_SET_CHILD_SUBREAPER, 1)`, starts `/bin/sh -c <script>` and then only calls `proc.Wait()` on that shell. Only after the shell has exited does `stopAdoptedChildren` reap and stop the children it adopted. While the check runs, an adopted orphan that exits therefore stays a zombie (state Z), because nobody reaps it until the shell is done. A check that kills a process group and then waits for its members to disappear sees the zombie as still present (`kill -0` succeeds on a zombie) and hangs until its own timeout, then fails. The same check passes without the helper.

Outcome (the product should do this): the helper reaps every child that exits while the shell runs, not only after it.

Required behavior, precisely (`runAcceptanceReaper` in `verify/sweep_linux.go`):
- Instead of `proc.Wait()`, the helper waits for any child with blocking `syscall.Wait4(-1, &status, 0, nil)` in a loop, retrying on `EINTR`, until the returned pid is the shell's pid. Every other pid returned is an adopted (or other) child that has just been reaped. Its status is discarded. The shell's own wait status is kept and returned exactly as today: `ws.Signaled()` gives `128 + int(ws.Signal())` (for example 143 for SIGTERM); otherwise the exit code. This holds even when an adopted orphan is reaped before the shell. (Do not also call `proc.Wait()` for the shell after `Wait4` has reaped it.) A `Wait4` error other than `EINTR` before the shell has been seen cannot happen while the shell is a child; treat it like today's `proc.Wait` error and return 127.
- Nothing is signalled while the shell runs.
- Once the shell has exited, `stopAdoptedChildren()` runs exactly as today: SIGTERM once to each same-uid child during `sweepGrace` (5 s), SIGKILL on later passes, EPERM children skipped, about 25 ms between passes, until a snapshot shows none. Detached servers that outlive the check are therefore still stopped before the helper returns.
- No other behavior changes. These stay exactly as they are: the flag `--kogen-verification-acceptance-reaper` and the `init` dispatch; `acceptanceReaped`; the environment handling (the shell gets the helper's environment and stdio); the `prctl` refusal fallback (`syscall.Exec` of `/bin/sh`); status 127 for a shell that cannot start; the catching of SIGINT, SIGTERM and SIGHUP; `stopAdoptedChildren`, `listProcs`; the marker sweep and every caller (`verify/run.go`, `verify/env.go`, `verify/probe.go`, `verify/concurrent.go`). macOS (`sweep_darwin.go`) and other platforms (`sweep_other.go`) are untouched. `sweepGrace` and `StepTimeout` are unchanged.
- Doc comments: the comments of `acceptanceReaped` and `runAcceptanceReaper` say that the helper reaps children that exit while the command runs, and stops and reaps the rest once the shell has ended. Nothing is removed. The existing workaround in `verify/probe_deadline_test.go` (`trap 'wait; exit 143' TERM; ...`) may stay as it is.

Acceptance harness: the step file builds, once per run with `go build -overlay`, the virtual package `./features/steps/testdata/acceptancereaper`. It writes no file into the checkout. This is a `main` package that blank-imports `github.com/KogenAI/kogen-verification/verify`, so the package's own `init` turns that binary into the real helper when it is started with the flag. Each scenario runs `/bin/sh -c "exec <harness> --kogen-verification-acceptance-reaper '<script>'"` in a fresh directory. The script's environment is the run's environment plus `FIXTURE_NODE` (this Node), `FIXTURE_HARNESS` (the harness, whose `launch <file>` mode is the Go launcher of a detached server), `GOFLAGS=`, `GOWORK=off`, `GOTOOLCHAIN=local` and `GOPROXY=off`. The harness's `control-good`/`control-bad` modes are independent control subreapers. They are used only by the observer controls (Feasibility), never by the scenarios.

Build notes: this runner is Linux (Go 1.27.2, dash as /bin/sh, util-linux `setsid`, python3, perl, Node 24.21.0). Add Linux-only Go tests to `verify/sweep_linux_test.go`. That test binary links `verify`, so `exec.Command(os.Args[0], acceptanceReaperFlag, script)` runs the real helper.

## Decisions
- While the shell runs, the helper waits for any child (`Wait4(-1)`), so an adopted orphan that exits is reaped at once and never lingers as a zombie (source: request)
- The shell's own wait status is kept and returned exactly as today (exit code, or 128+n for a signal n), even when an adopted orphan is reaped before the shell (source: request)
- Nothing is signalled while the shell runs; once the shell has exited, the remaining children are stopped and reaped as today (SIGTERM once, SIGKILL on later passes, until a snapshot shows none) (source: request)
- The helper's flag, its environment handling, its status for a failed start (127) and the orphan sweep stay as they are (source: request)
- Linux only (source: request)

## Source comparison
- Problem (an adopted orphan that exits stays a zombie until the shell ends, so a group-gone wait hangs to the timeout): addressed by the `Wait4(-1)` loop in `runAcceptanceReaper`.
- Synthetic acceptance 1 (a background `sleep 300` in its own process group, killed with `kill -TERM -- -<pgid>`, polled with `kill -0` for up to 5 s, printing `gone` or `still present`; `gone` within 0.5 s after the change, `still present` (state Z) before): scenario `A process-group member adopted by the helper and killed while the shell runs is gone at once`. The member is started with `( setsid /bin/sleep 300 ... & )`, so it is in its own process group and has been adopted by the helper. The script waits until the group exists and prints `member adopted by the helper` when the member's parent is the helper. It kills with `kill -TERM -$member`, because dash's builtin `kill` rejects `--` ("Illegal number: -", observed in a scratch run). It writes the milliseconds from the kill to the end of the poll into `elapsed-ms`, which must be at most 500. On `still present` it writes `state <S>` to standard error.
- Synthetic acceptance 2 (`echo hi; exit 4` returns 4 with `hi`; a script that kills itself with TERM returns 143; both unchanged): scenario `The helper still returns the shell's exit code and 128+n for a signal` (`kill -TERM $$`).
- Synthetic acceptance 3 (detached servers in python, node, perl and go: new session, empty environment, descriptors closed, launcher exited; after the helper returns none is running): scenario `Detached servers of python, node, perl and go keep running while the shell runs and are stopped before the helper returns`. The launchers are Python `subprocess.Popen` (`env={}`, `start_new_session=True`, `close_fds=True`, DEVNULL stdio); Node `spawn` (`detached`, `env: {}`, `stdio: 'ignore'`, `unref`); Perl `fork` + `setsid`, closing descriptors 3..255, `/dev/null` stdio, `%ENV = ()`, `exec`; and the harness's Go `launch` mode (`Setsid`, empty `Env`, no extra descriptors). Each writes the server's pid and exits. The script also prints, for each server, that it is still running, in its own session and adopted by the helper 0.5 s later. This covers "nothing is signalled while the shell runs".
- Synthetic acceptance 4 (a background child exits before the shell, then `sleep 1` and `exit 7`; the helper returns 7): scenario `Children that exit before the shell do not change the helper's status`. It covers a direct background child exiting 9, an adopted orphan exiting 9 and an adopted orphan killed by SIGKILL, so a wrong status of 9 or 137 is told apart from 7.
- Synthetic acceptance 5, first half (the existing orphan-sweep tests pass unchanged): covered by the configured `go-test` check (`TestAcceptanceStopsMarkerlessSessionOrphan`, `TestAcceptanceStopsDetachedServers`, `TestAcceptanceStopsMarkerlessChildOfMarkedProcess`, `TestAcceptanceLeaves*`, `TestStep*`, `TestAcceptanceReapedQuotesScript`). Acceptance does not repeat them, because of the 120-second step limit.
- Synthetic acceptance 5, second half (a test that kills a process group and waits for it to be gone, run as the check under the helper, passes within its own time): scenario `A Go test that kills a process group and waits for it to be gone passes as the check under the helper`. A fixture Go module's `TestGroupGone` starts `/bin/sh -c '/bin/sleep 300 & echo $!; wait'` as a new process group and SIGKILLs the group. It waits for the shell, then polls `kill(member, 0)` for at most 5 s. The check is `go test -count=1 -run '^TestGroupGone$' -v .` under the helper.
- "Builds whose check runs such a test fail at the timeout": the end-to-end entry point is the helper itself, which every check, acceptance run and probe goes through. No new Kogen-level scenario is added.

## Tests
- While the shell runs, an adopted orphan that exits is reaped at once, so a killed process-group member is gone: new Linux test in `verify/sweep_linux_test.go` that runs the test binary as the helper on a script that adopts a `setsid` member, kills its group and polls `kill -0`, expecting `gone` (regression); scenarios `A process-group member adopted by the helper ...` and `A Go test that kills a process group ...` (scenario)
- The helper returns the shell's status, not that of a child reaped before the shell: new Linux test in `verify/sweep_linux_test.go` with an adopted orphan exiting 9 before the shell exits 7, expecting 7 (integration); scenario `Children that exit before the shell do not change the helper's status` (scenario)
- The exit code and 128+n for a signal are unchanged: scenario `The helper still returns the shell's exit code and 128+n for a signal` (scenario)
- Nothing is signalled while the shell runs, and detached servers are stopped before the helper returns: scenario `Detached servers of python, node, perl and go ...` (scenario); existing `TestAcceptanceStopsMarkerlessSessionOrphan`, `TestAcceptanceStopsDetachedServers` (existing)

## Feasibility

The two missing-feature scenarios' fixtures, run under a control subreaper that waits only for the shell (today's behavior), print `still present` with `state Z`-style residue after about 5050 ms, and `TestGroupGone` fails.
