# Stop detached servers an acceptance run started

Slug: k-verify-orphan-sweep
Model: not applicable — the change adds one attribution rule to the one-shot sweep after a single acceptance command; nothing persists between runs and no rules interact over time
Acceptance:
- .kogen/intents/k-verify-orphan-sweep/acceptance.feature
- features/steps/orphan_sweep_steps.js
- features/steps/testdata/sweepdriver/main.go

Studio issue f8d0ce5a (kogen; reported by kogen-research-owner, 3 Nov 2026), K-VERIFY-ORPHAN-SWEEP, change_type fix, package `verify` (`verify/sweep.go`, called from `verify/run.go` `RunAcceptance`).

Today, after the acceptance command returns, `RunAcceptance` stops the processes the run started in two ways. It matches processes carrying the per-run environment entry `KOGEN_ACCEPTANCE_RUN=<value>`, and it follows parent-pid descent from those marked processes. A background server can clear its environment, start a new session, and be reparented to pid 1 when its launcher exits. That server matches neither rule, so it keeps running after the run. On macOS, a server that is an Apple platform binary (for example `/bin/sleep`) hides its environment from other processes, so even a new-session server that kept its environment survives there. This was reproduced on this macOS runner: of the six fixture patterns below, the patterns `setsid, env kept` and `env cleared, setsid, launcher exited` survive. On Linux, only the second survives, per the report.

Outcome: every acceptance run gets a second marker that survives environment clearing, a new session and reparenting. This is a per-run marker file that the acceptance shell holds open on file descriptor 9. Every process the command starts inherits that descriptor unless it closes it. When the run ends, the sweep also stops every process of the current user that holds an open descriptor on that run's marker file, together with that process's descendants. It does this on Linux and on macOS, through the same SIGTERM, grace and SIGKILL sequence as today. The environment marker and parent-pid descent stay as they are. Processes the run did not start are never signalled: other runs, other Builds, the user's own processes, Kogen itself and its ancestors. The run's exit status and output stay exactly as today, and so does the command text Kogen records and logs.

Required behavior, precisely:
- Interface unchanged: `func RunAcceptance(ctx context.Context, s *sys.Session, root string, tools Tools, slug, command, report string, ev Evidence, log Logger) (Acceptance, error)`. It keeps the same arguments, the same `Acceptance` fields (`Status`, `Output`, scenarios, problems) and the same errors. No new CLI command, flag or setting. No timeout is raised: `sweepGrace` stays 5 seconds and `StepTimeout` stays 120 seconds.
- Marker file: before the command starts, `RunAcceptance` creates a new, empty regular file of its own. It has mode 0600, a unique name, and lives in Kogen's temporary area (for example through `sys.TmpPath` or `os.CreateTemp`). The file is removed after the sweep, however the run ends: normal end, error, interrupt or timeout. If the file cannot be created, `RunAcceptance` returns that error before anything starts, the same way it already handles a run value that cannot be generated. Kogen's own process does not keep the file open while the command runs.
- Execution: the configured command runs exactly as today, as the single `-c` argument of `/bin/sh` (so `$0` is `/bin/sh`, and parsing, syntax-error messages and line numbers are unchanged). It runs in the same process that `sys.Session.Run` starts (same pid, process group, supervisor, `KillGroupOnExit`, timeout and interrupt handling) and in the same environment (`KOGEN_ACCEPTANCE_FEATURES`, `KOGEN_ACCEPTANCE_REPORT`, `KOGEN_ACCEPTANCE_RUN`). The only addition is that the shell holds the marker file open for reading on descriptor 9 before the configured command starts. The form observed to meet all of this is to pass this text to the existing `runStep`/`sys.Session.Run` path: `exec 9<'<marker path>'; exec /bin/sh -c '<configured command>'`. Here both values are single-quoted with each `'` written as `'\''`, so the inner `/bin/sh` receives the configured command byte for byte. Do not prefix the configured command's own text: bash as macOS `/bin/sh` echoes the whole command line in a syntax error, so prefixing would change the output.
- Records unchanged: the `command` log event, the `AttemptStep.Command` of the acceptance step (redacted as today) and the command text used by `RunWatched` all show the configured command, not the text that holds the marker.
- Selection: `acceptanceTargets` keeps its rules: current user only; never Kogen's own process (`self`), its ancestors or zombies; descendants by parent pid of a selected process. Its `marked` predicate becomes true for a process that does either of these:
  - its environment holds exactly `KOGEN_ACCEPTANCE_RUN=<this run's value>` (as today);
  - it has an open descriptor, with any number, on this run's marker file, compared by device and inode taken from `os.Stat` of the marker.
  A descriptor or environment that cannot be read does not match. Linux reads `/proc/<pid>/fd/*` (`os.Stat` of each entry follows it to the file). macOS uses `proc_info`: `PROC_PIDLISTFDS` lists the process's descriptors, then `PROC_PIDFDVNODEINFO` is read for each vnode descriptor. In `struct vnode_fdinfo`, `vst_dev` (uint32) is at byte offset 24 and `vst_ino` (uint64) at offset 32. This was observed to read descriptors of Apple platform binaries. Other platforms keep today's "process table unsupported" result.
- Sweep sequence unchanged: SIGTERM to the targets; SIGKILL to those still present after the grace; then snapshots and SIGKILL until a snapshot finds none. A process that refuses a signal (EPERM) is not waited for again. A process table that cannot be read is logged as `acceptance_sweep_unavailable` and is not an error of the run.
- Boundary, stated rather than solved: a process is still not attributable when it drops both markers (it clears its environment and closes descriptor 9) and also leaves the session and loses its marked parent. Two launchers observed to drop descriptor 9 are Node's `child_process.spawn` on macOS (posix_spawn closes inherited descriptors) and Python's `subprocess` with its default `close_fds=True`. The same applies when the configured command itself closes or reuses descriptor 9: processes it starts after that rely on the environment marker and parent-pid descent, as today. macOS has no unprivileged way to contain such a process. This Intent adds no Kogen-wide subreaper, re-exec helper, cwd heuristic or time-window heuristic, because each of those could signal processes the run did not start.

Replaced: the doc comment of `RunAcceptance` and of `stopAcceptanceProcesses` ("every process it started that carries the run's value, with their descendants") is updated to say processes carrying the run's value or holding its marker descriptor, with their descendants. Nothing is removed.

Build notes: Linux could not be probed in this session, so check that the Linux file compiles and vets with `GOOS=linux go build ./...` and `GOOS=linux go vet ./verify`. New Go regression tests need a launcher that keeps inherited descriptors, for example the shell, a Go `os/exec` launcher, or python3 with `os.fork`/`os.setsid`/`os.execve` or `close_fds=False`. Python's default `Popen` is outside the guarantee. The acceptance harness `features/steps/testdata/sweepdriver/main.go` sits in a `testdata` directory, so `go build ./...`, `go vet ./...` and `go test ./...` skip it, but the `format` check (`gofmt -l .`) still covers it. The acceptance steps build it with `go build -o <temp>/sweepdriver ./features/steps/testdata/sweepdriver` from the project root.

## Decisions
- The run's exit status and output stay exactly as today; the recorded and logged acceptance command stays the configured command (source: request)
- Processes the run did not start (other runs, other Builds, the user's own) are never signalled; where full attribution would require a heuristic that could signal them, the process stays unattributed instead (source: request)
- No new CLI commands or flags and no timeout raised (source: request)
- Synthetic regression tests only: one fixture acceptance command per reported pattern, survivor check 1.5 s after RunAcceptance returns, no model and no AoR task (source: request)

## Source comparison
- Problem and evidence (six patterns: plain `&`, nohup, setsid with env kept, `env -i` same group, `(env -i x &)` same group, env cleared + setsid + launcher exited; survivor check 1.5 s after RunAcceptance returns): addressed. acceptance.feature runs each pattern by name through `verify.RunAcceptance` with the harness `features/steps/testdata/sweepdriver/main.go`. macOS has no `setsid` command, so the harness's own `spawn -setsid [-clearenv]` launcher (Go `os/exec`, exits without waiting) stands in for setsid and the exiting launcher. The server is `sleep 300` (`/bin/sleep` on macOS, a platform binary).
- macOS note (platform binary hides its environment, so the env-kept setsid case survives): addressed by the descriptor marker; scenario `setsid, env kept`.
- Need, "every process an acceptance run started is stopped ... including detached servers that cleared their environment and left the session": addressed for every process that keeps the inherited descriptor 9 or the environment marker, or descends from one that does. Partly conflicting: a process that drops both markers and also detaches stays unattributable (see Boundary). On macOS this is a platform limit (no subreaper or other unprivileged containment). On Linux the subreaper route is not taken, for the reason under "Constraint, blind patch" below.
- Need, "processes the run did not start ... are never signalled": addressed. Every pattern scenario also checks three processes that must still be running: a detached, environment-cleared process the harness starts before the run; one with the same shape that it starts while the run is running; and a harness child that carries another run's `KOGEN_ACCEPTANCE_RUN` value. Existing `TestAcceptanceLeavesOtherRunsProcessesAlone` and `TestAcceptanceTargets` stay.
- Need, "the run's exit status and output stay exactly as today": addressed. Every pattern scenario checks status 3 and output `fixture output\nfixture error\n`. Two scenarios compare RunAcceptance with `/bin/sh -c` run directly: a syntax error (`echo start; fi`, status 2) and `echo "$0"; echo out; echo err >&2; exit 4` (status 4, output `/bin/sh\nout\nerr\n`).
- Constraint, synthetic regression tests only, no model, no AoR task: addressed (fixture commands and Go regression tests).
- Constraint, no new CLI commands or flags, no timeout raised: addressed (Required behavior, Interface unchanged).
- Constraint, the evidence and fixture notes at `~/Scratch.noindex/kogen-lanes-private/notes-harness/climb/verification/SHELF-leftover-orphan-sweep.md` and `LANE.md` ("Row 14 / f8d0ce5a"): not readable in this session, because the directory does not exist on this runner. The fixture patterns come from the request text, so the launcher used by the research fixture is unknown here. If it closes inherited descriptors (for example Python's default `subprocess.Popen`) and clears the environment, the Boundary applies.
- Constraint, blind patch (Linux subreaper through a re-exec helper), reference only: not used. A subreaper on Kogen's own process without a helper would also take in detached processes that Kogen itself starts during the run, and could not tell which run they belong to. The `during` process in every pattern scenario is the counterexample.
- Research screens the landed head with the same fixture on eu2 and the Studio runner: outside this Intent (after delivery, by research).

## Tests
- A server that cleared its environment, started a new session and was reparented when its launcher exited is stopped when the run ends, on Linux and macOS: new regression test in `verify/sweep_test.go`, RunAcceptance on such a fixture (launcher keeps inherited descriptors), server gone within 5 s after it returns (regression); scenario `env cleared, setsid, launcher exited` (scenario)
- On macOS, a new-session server that kept its environment but is an Apple platform binary (`/bin/sleep`) is stopped: new regression test in `verify/sweep_test.go` (darwin, `/bin/sleep`) (regression); scenario `setsid, env kept` (scenario)
- Plain `&`, nohup, `env -i` same group and `(env -i x &)` same group servers are still stopped: scenarios `plain &`, `nohup`, `env -i, same group`, `(env -i x &), same group` (scenario)
- A process holding a descriptor on the run's marker file is selected, and one holding another file is not: new integration test of the platform descriptor check (Linux `/proc`, macOS `proc_info`) against real child processes (integration)
- Processes the run did not start are never signalled (a detached environment-cleared process started before or during the run, another run's value, Kogen's own child, Kogen's ancestors, other users, zombies): existing `TestAcceptanceTargets` and `TestAcceptanceLeavesOtherRunsProcessesAlone` (existing); new integration test that a detached, environment-cleared process the test starts while the run is running survives (integration); the three unrelated processes in every pattern scenario (scenario)
- The run's exit status and output are exactly those of `/bin/sh -c <command>`, including a syntax error and `$0`: scenarios `A command with a syntax error reports what sh reports` and `A command's name, output and exit status are its own` (scenario)
- The acceptance step's recorded and logged command stays the configured command: new integration test that the `AttemptStep.Command` of the acceptance step and the `command` log event of RunAcceptance equal the configured command (integration)
- The marker file exists only for the run: new integration test where the command records the path it holds on descriptor 9 (`/dev/fd/9` on macOS, `/proc/self/fd/9` on Linux) and the file is gone after RunAcceptance returns (integration)

## Feasibility
- Unchanged tree, this macOS runner (Darwin 25.6, arm64, Go 1.27.2, Node 24.21.0): the harness reproduces the report. `setsid, env kept` and `env cleared, setsid, launcher exited` servers are running 1.5 s after RunAcceptance returns; the other four are stopped; the unrelated processes are running; status 3 and output exact. (local scratch probe in this session, not a Kogen record: cucumber on acceptance.feature, 8 scenarios, 6 passed, 2 failed, 17 s)
- A scratch prototype of the descriptor marker (not submitted) made all 8 scenarios pass (17 s), and `go test -count=1 ./...` still passed (69 s). It held the marker with `exec 9<'<marker>'; exec /bin/sh -c '<command>'`, and its sweep also selected processes with a descriptor on the marker's device and inode through `proc_info` `PROC_PIDLISTFDS`/`PROC_PIDFDVNODEINFO`. (local scratch probe in this session)
- macOS `proc_info` reads the descriptors of a same-user Apple platform binary (`/bin/sleep`) whose environment `kern.procargs2` hides. (local scratch probe in this session: prototype stopped both macOS survivors)
- Two launchers do not pass descriptor 9 to their child: Node 24.21.0 `child_process.spawn` (detached, `env: {}`) on macOS, and Python 3.13 `subprocess.Popen` with default `close_fds`. `lsof` shows no marker in the child, so this is the Boundary. (local scratch probe in this session)
- Prefixing the command text would change syntax-error output under macOS `/bin/sh` (bash echoes the whole line). Passing the command unchanged to an inner `/bin/sh -c` kept status 2, identical output, and `$0` as `/bin/sh`. (local scratch probe in this session)
- Linux was not probed in this session (no Linux host). The Linux selection relies on `/proc/<pid>/fd`; the Build checks compilation with `GOOS=linux`.
