# Reap markerless acceptance orphans on Linux

Slug: k-verify-orphan-sweep-closefd
Model: not applicable — the change adds one per-run, one-shot stop step (TERM, grace, KILL, reap) after a single acceptance command; nothing persists between runs and no rules interact over time
Acceptance:
- .kogen/intents/k-verify-orphan-sweep-closefd/acceptance.feature
- features/steps/orphan_sweep_steps.js
- features/steps/testdata/sweepdriver/main.go

K-VERIFY-ORPHAN-SWEEP-CLOSEFD. Package `verify`: `verify/sweep_linux.go` (with `verify/sweep_darwin.go` and `verify/sweep_other.go` for the per-platform no-op), and the `RunAcceptance` call site in `verify/run.go`.

Today (landed in 6ac87f0), `RunAcceptance` sweeps the acceptance run's leftover processes after the command returns. It finds them by the environment entry `KOGEN_ACCEPTANCE_RUN=<run value>` or by an open descriptor on the run's marker file (held on descriptor 9 by the acceptance shell), plus parent-pid descent from those. A server launched with a cleared environment, in a new session, by a launcher that closed inherited descriptors and then exited, carries neither marker and has lost its marked parent (ppid 1). Nothing finds it, so it survives the run. Python's `subprocess.Popen` closes descriptors by default (`close_fds=True`). Node, Ruby and Go launchers are expected to behave the same way, but this was not measured. This survival was reproduced on this macOS runner on the unchanged tree with both new fixture patterns (see Feasibility).

Outcome: on Linux, an acceptance run leaves no process of its own tree alive, however the launcher treats descriptors and environment. Every acceptance command on Linux runs under a dedicated per-run helper process that is a child subreaper (`prctl(PR_SET_CHILD_SUBREAPER, 1)`). Every descendant of the command whose parent dies is reparented to the helper instead of pid 1. Once the command's shell has ended, the helper stops and reaps all of its remaining children. macOS has no subreaper and keeps today's marker sweep unchanged; there such a server remains outside the guarantee. The existing marker sweep still runs after every run on Linux and macOS. Processes the run did not start are never signalled. The run's exit status and output, and the command text Kogen records and logs, stay exactly as today.

Required behavior, precisely:
- Interface unchanged: `func RunAcceptance(ctx context.Context, s *sys.Session, root string, tools Tools, slug, command, report string, ev Evidence, log Logger) (Acceptance, error)` keeps the same arguments, `Acceptance` fields and errors. No new CLI command, flag, setting or environment variable. No timeout is raised: `sweepGrace` stays 5 seconds and `StepTimeout` stays 120 seconds.
- Call site (`verify/run.go`): the `script` argument of `runStepAs` becomes `acceptanceReaped(acceptanceScript(markerFile, command))` (any name will do). The `command` argument stays the configured command, so the `command` log event, `AttemptStep.Command` and the text `RunWatched` shows stay the configured command. The marker file, the `KOGEN_ACCEPTANCE_*` environment and the deferred `stopAcceptanceProcesses` sweep stay exactly as they are.
- macOS (`sweep_darwin.go`) and other platforms (`sweep_other.go`): the wrapper returns the script unchanged, so behavior is exactly as today.
- Linux wrapper: the script becomes `exec '<self>' --kogen-verification-acceptance-reaper '<script>'`, where `<self>` is `os.Executable()` and both values are single-quoted with the existing `shellQuote`. If `os.Executable()` fails, the script is passed unchanged, and the marker sweep alone applies as today.
- Helper dispatch (Linux): an `init()` in the Linux file of package `verify` becomes the helper only when `os.Args` is exactly `[<self>, "--kogen-verification-acceptance-reaper", <script>]`. Otherwise it returns at once. It therefore works before `main` in every binary that links `verify`: the `kogen` program, Go test binaries and the acceptance harness. Only this helper process ever becomes a subreaper. Kogen's own process and any embedding program never change their adoption policy, because a Kogen-wide subreaper would adopt processes of concurrent runs and Kogen's own detached children.
- Helper behavior (Linux), in order:
  1. Call `prctl(PR_SET_CHILD_SUBREAPER, 1)` (option 36). If the kernel or sandbox refuses it, `syscall.Exec` `/bin/sh -c <script>` with the same environment (today's behavior; the marker sweep then applies). Exit 127 if even that exec fails.
  2. Catch SIGINT, SIGTERM and SIGHUP with `signal.Notify`; do not ignore them. The command then inherits default dispositions, and the helper outlives a group signal so that it can still clean up. The `sys` supervisor keeps owning process-group cancellation, timeout and interrupt.
  3. Start `/bin/sh -c <script>` with the helper's stdin, stdout, stderr and environment, and wait for it. Exit 127 if it cannot start.
  4. Stop the adopted children. Repeat this loop until a snapshot shows no remaining child:
     - First reap every exited child with `wait4(-1, WNOHANG)`.
     - Then take a `listProcs()` snapshot and select every process whose parent is the helper and whose uid is the helper's, skipping processes that refused a signal.
     - Send SIGTERM once to each selected process while the grace (`sweepGrace`, counted from the start of this step) lasts, and SIGKILL on every pass after the grace.
     - A process that answers EPERM is not signalled or waited for again.
     - Sleep about 25 ms between passes.
     The loop ends because every same-uid child is either killed (SIGKILL cannot be refused) and then reaped, or refused and skipped. If the snapshot cannot be read, stop and leave cleanup to the marker sweep. The helper signals only its direct children; PIDs cannot be recycled between snapshot and signal, because it reaps only at the top of a pass. Killing a parent makes that parent's surviving descendants the helper's children on the next pass, even if they are in a new session with an empty environment.
  5. Exit with the shell's exit status. If the shell was killed by signal n, exit 128+n. This is the status `sys` already reports today for a signalled command, for example 143 for SIGTERM and 137 for SIGKILL.
- Interrupt and timeout (unchanged ownership): `sys` signals the process group as today. Because the helper catches the group signals, it still runs step 4 after the shell ends, unless `sys`'s own SIGKILL ends it first. The marker sweep runs after it in every case.
- `$0`, parsing, syntax-error messages and output stay those of `/bin/sh -c <configured command>`, because the helper runs the unchanged `acceptanceScript`, which ends in `exec /bin/sh -c '<configured command>'`.

Replaced: the doc comment of `RunAcceptance` gains one sentence saying that on Linux a per-run subreaper also stops descendants that carry neither marker. Nothing is removed.

Build notes: this runner is macOS (no Linux host, VM or container). Linux code is compiled here only through `GOOS=linux go vet ./...`, which acceptance runs; the configured checks do not compile it. The new Linux regression test (`verify/sweep_linux_test.go`, `//go:build linux`) runs only on Linux. Reuse the existing test helpers `sweepPython`, `sweepRoot`, `sweepPIDs` and `sweepGoneSoon` from `verify/sweep_test.go`. The acceptance harness `features/steps/testdata/sweepdriver/main.go` sits in `testdata`, so `go build/vet/test ./...` skip it, but `gofmt -l .` still covers it.

## Decisions
- On Linux, no process of the acceptance run's own tree survives the run, regardless of how the launcher treats descriptors and environment; the reported case is Python `subprocess.Popen` with default `close_fds`, `env={}`, a new session and an exiting launcher (source: request)
- macOS has no subreaper and keeps the marker sweep unchanged (source: request)
- The change is confined to `verify/sweep*.go` and the `RunAcceptance` call site in `verify/run.go` (source: request)
- Processes the run did not start are never signalled, and the run's exit status and output stay identical (source: request)

## Source comparison
- Problem (env cleared + new session + launcher exited + inherited descriptors closed survives, ppid 1): addressed on Linux by the per-run subreaper helper. - Evidence, check 6ac87f0 (six-pattern fixture 5/6; only "env cleared + setsid + launcher exited" survived there with `close_fds` left at its default; with `close_fds=False` the candidate swept it; bystanders alive 12/12; exit status and output identical for 4 commands; Linux only): The six landed patterns stay stopped on both platforms (second scenario outline). Bystanders are checked in every pattern scenario: a detached, environment-cleared process started before the run, one started while it runs, and a process carrying another run's value. Exit status and output identity is checked with four commands: a syntax error, `$0`/output/exit 4, SIGTERM (143) and SIGKILL (137). The four commands of the check are not named in the request; these four were chosen to cover the helper's status pass-through.
- Evidence, Darwin table pending: not available. On this macOS runner both new patterns survive on the unchanged tree (Feasibility), and macOS keeps that boundary.
- Reference implementation (Linux self-exec subreaper helper, 6/6 on the Linux fixture): the mechanism is adopted with these deviations. It wraps today's `acceptanceScript` (the reference predates `runStepAs`/fd 9 and wrapped the bare command). The helper is entered through `exec`. The function is named after what it wraps. Its regression test is kept as `TestAcceptanceStopsMarkerlessSessionOrphan`.
- Not shown that the residual occurred in the original EU hang (f8d0ce5a); no AoR cell left a server: noted, and no claim is made.
- Independence (`verify/sweep.go` and the `verify/run.go` call site only): addressed. The Linux helper lives in `verify/sweep_linux.go`, with no-op wrappers in `sweep_darwin.go`/`sweep_other.go`. The acceptance harness and its steps change only to add the two fixture patterns, the `-closefds` launcher flag, the Linux-only judgement step and the Linux vet step.
- Gate X-V1 (which launchers survive: node, ruby, go): not measured here. The mechanism does not depend on the launcher. The Go closing launcher stands in for "launcher closed inherited descriptors"; Node and Ruby fixtures are not added.
- Platform limit of this runner: acceptance runs on macOS here, where the Linux judgement step records what it saw instead of judging it. On this runner, the new outline passes on the unchanged tree. It distinguishes the change only where acceptance runs on Linux.

## Feasibility
- Unchanged tree, this macOS runner (Darwin 25.6, arm64, Go 1.27.2, Node 24.21.0, Python 3.13.16): both new patterns reproduce the residual. The server is `running` 1.5 s after RunAcceptance returns, while all three bystanders keep running and status/output are exact. The landed `env cleared, setsid, launcher exited` pattern (Go launcher that keeps descriptors) is stopped. (local scratch run in this session, not a Kogen record)
- The draft acceptance (13 scenarios) passes on this macOS runner both on the unchanged tree and with a scratch Linux helper prototype. On macOS this is expected, because the wrapper is a no-op there; the Linux judgement step logs instead of asserting. (local scratch run, 24 s)
- A scratch prototype of the Linux helper on the current tree (`init` dispatch, `prctl` option 36, `/bin/sh -c` child, wait4/listProcs TERM/grace/KILL loop, 128+n exit) passes `GOOS=linux go vet ./verify` and darwin `go vet ./verify`. It was not run on Linux: there is no Linux host here. `GOOS=linux go vet ./...` on the unchanged tree takes about 5 s. (local scratch runs)
- RunAcceptance on this runner reports a command killed by SIGTERM as status 143 and by SIGKILL as 137, the same as a helper that exits 128+n. Direct `/bin/sh -c` in Go reports -1 for both, so the signal scenarios check exact status rather than comparing with `sh -c`. (local scratch run of `sweepdriver same`)
